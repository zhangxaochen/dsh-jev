# dsh-jev 0.3.0 计划：社区扫描的借鉴落地

> **依据**：本会话的社区开源生态扫描（Jev/TypeSafe 生态的高星项目、官方侧跟进、独立评测，含负面结果）。该扫描本身**未入库**——`docs-consistency.spec.ts` 会校验 `docs/research.md` 里 `docs/…`/`tests/…` 形式的路径必须存在，而会话产物所在目录不入库，因此本文件与 `research.md` 都**不写该路径**，只写"会话产物"。
> **执行规则**：每完成一项，代码/文档 + 本文件一起提交；每一项都必须留下一个**闸门**或一条**明示的测量结论**。测量推翻假设时，写明推翻过程（这是本仓库已有的纪律）。
> **起点版本**：`0.2.0`（HEAD 已含 README 拆分、`docs/configuration.md`、`docs/releasing.md`、`headlessAsk` 默认 `warn`）。

### [x] 1.3 判定不可达**可见**且**可测**

现状（这是本批最有价值的一项）：`onError` 失败路径只做两件事——`recordSafetyInspectionFailure()` 与 `console.warn`，**不写决策记录**；指标是聚合计数、无时间戳。因此"失败是成簇（上游真出事）还是孤立点（单次抖动）"今天答不了，用户也只能看到历史累计，分不清"上个月抖过 3 次"和"此刻正在降级"。

- 照抄同一文件里 `headlessAsk` 的 `warn` 路径：`recordSafetyCheck(...)` + `defaultDecisionLog.append({ module, action, detail: { reason, tool, commandPreview } })`，并复用已实现的 `redactSecrets`（凭据不进日志）。

**验收**：失败在 `~/.dsh/jev-decisions.jsonl` 里带时间戳（1.3a）；若做 1.3b，看板能区分"历史累计"与"当前降级"。

**结论（2026-09-20，已实现 1.3a + 1.3b）**：实机累计 **390/717（54%）** 次审查落在失败路径上（口径：文件生命周期累计，含 `calibration.md` §23 修复前那一段，**不等于当前失败率**）。"几乎不发生"因此被排除，故 1.3b 一并做（展示的边际成本为零）。原计划里更重的那一步——给审查 state 设上限或摘要——**未做**：它改动判定输入，必须先有带时间戳的记录给出"当前的"失败率与形态分布。原始数字、口径与下一步见 `docs/calibration.md` §26。

## 批次 2 — 两个测量（结论决定后续项做不做）

### [x] 2.1 state 变长后的准确率漂移（官方文档自认的 jaggedness）

这不是"数字洁癖"，是**安全未知量**：`safety-guard` 的每次审查、每条用户规则，都是"state（会话上下文）+ 若干问题"一次发出的；若准确率随 state 变长漂移，那么"长会话里的安全裁决是否还准"没有任何数据，而它守的是破坏性命令、凭据外泄与文件写入。

- 新增探针（沿用 `tests/probe.ts` 的形状）：固定问题集合、固定候选，仅改变 `state` 长度（建议 0 / 4K / 16K / 48K 字符四档，每档重复数次），记录每个桶概率与 `confidence` 的漂移。
- 结论写入 `docs/calibration.md` 新一节，并给出**处置**：漂移超阈值 → 给审查路径的 state 设上限或做摘要（真改动）；漂移可忽略 → 明确关闭该风险，免得后来者再猜一次。

**验收**：calibration 有该节与原始数字；处置写完（"关闭风险"也是处置）。

**结论（2026-09-20，`pnpm run probe:jaggedness`，两次运行一致）**：审查路径的 state 就是被审参数，8 个客观标注用例 × 载荷 0/4K/16K/48K 字符，准确率始终 **1.00**（@0.5 与守门的 @0.85 都是），类间分离度 **0.93–0.94**，延迟 377–632ms、0 错误。⇒ **在该包络内关闭此风险**，原计划里"给审查路径的 state 设上限或摘要"**不做**（无证据支持，且会改动判定输入）。局限已写明：单次采样、只覆盖两条 noul 问题、48K 以上无数据、单一模型版本。见 `docs/calibration.md` §27 与 `docs/calibration/probe-2026-09-20-jaggedness.json`。

### [x] 2.2 排序的基线对照

剪枝、skill 路由、`jev_rank` 全是打分排序，现有闸门（`bench` 36 条、`verify:pruner` 6/6、`verify:router` 6 PASS + 1 KNOWN）只证明"比什么都不做强"，**从未与零成本基线对照**。社区里最相关的一条证据恰是负面结果（检索重排上不如专用小模型）。

- 写一个**词法基线**（工具名/描述与请求的词元重叠打分），对同一批语料跑同一套标注，输出对照表。
- ⚠️ **反稻草人要求**：基线必须是"一个理性人会真的采用的做法"（名称匹配 + 词元重叠，必要时加同义词表），否则结论一定是"Jev 更好"，这一项就白做。写之前先说清基线的构造规则，跑完不许事后调参。
- ⚠️ **统计力有限**：可用语料只有几十条标注（剪枝 6、路由 7、bench 36），因此本项能判定的只是**量级差异**（"词法就够用" vs "Jev 明显更准"），不能当作严谨 benchmark。结论要按这个口径写，别过度解读。
- 判据：Jev 明显胜出 → 现有默认值有了依据；**打平 → 砍掉或简化对应模块**，省下每轮 250–700ms 与调用费。

**验收**：对照表写进 `docs/calibration.md`；若打平，本计划后续相关项一并撤销。

**结论（2026-09-20，`pnpm run probe:baseline`，两次运行一致）**：**不是打平**，故模块不撤销，但两臂证据强度不同：
- **路由**：Jev **6/7（85.7%）** vs 词法 **3/7（42.9%）**，差距明显；词法被 `acquisition-channel-advisor` 通吃（未加权重叠没有"哪个词重要"的概念）。代价 1026–1078ms/轮。
- **剪枝**：Jev **6/6（100%）** vs 词法 **5/6（83.3%）**——只领先 1 条用例，而代价是每轮 ~0.6s 与一次调用。⇒ 剪枝的收益**尚未被这批语料证明**，要判定需**扩大剪枝语料**（现 6 条），而不是重跑同样 6 条。
- 词法臂是**下界**（无 IDF/BM25、无同义词表、无双语映射），所以"路由只能靠模型"这种话不能从本结果推出。
- 未做：不改默认值、不把词法臂接进产品。另记录一次可用性观察：当日 `verify:pruner` 曾 2/6 因 >2000ms 超时返回全部候选（安全但没剪枝），重跑 6/6——剪枝路径没有独立超时预算。

细节见 `docs/calibration.md` §28 与 `docs/calibration/probe-2026-09-20-baseline.json`。

## 批次 3 — 路由的跨语言漏报

> **这两项是一件事**：3.1 只是 3.2 的解锁条件。若 3.2 实测收益小，两条一起删——别为了把 6/7 变成 7/7 去追一条标注用例，那有对单一样本过拟合的风险，而它的价值本来就不在准确率那半格。

### [x] 3.1 把 `verify:router` 从 6/7 修到 7/7

现有一条 `knownMiss`（`press-release`：中文请求选不中英文技能描述）。修法方向是让候选表示对上请求语言，而不是加豁免；修好后把该条的 `knownMiss` 标记去掉，让闸门恢复严格。

**结论（2026-09-20，`pnpm run verify:router` → 7/7）**：**原因不是语言**。三次实验：① 在问题里加"请求可能是另一种语言"的提示 → **更差**（SWOT 从通过变失败）；② 两段式（前 5 名再用一次 `choice` 比较）→ 新闻稿仍错，但对 SWOT 有效；③ 查目录元数据 → 真相是 `skills.list()` 的条目带 `invocation.modelInvocable`，而插件只映射了 `name/description/whenToUse`，把**用户专属技能**也送去排序。本机 **112 项中 20 项** `modelInvocable: false`（含获胜的 `writing-shape` ⇒ 路由器建议模型载入一个模型载入不了的技能）。
修法：`toCandidates` 过滤 `modelInvocable === false`（字段缺失视为未声明、保留），`shouldRoute` 的规模门槛改数**可载入**条目。修复后新闻稿选中 `press-release`（1.76/conf 0.63）、其余 6 条不变，`knownMiss` 标记删除。这不是为一条用例打的补丁——注入模型无法执行的建议在任何用例上都是错的。顺带：候选 112 → 92，正好是 3.2 要测的成本项。

### [x] 3.2 实测候选裁剪（`maxCandidates`）的延迟收益

`maxCandidates` 默认 0（不裁剪）的**唯一理由**就是 3.1 那类跨语言丢项风险；而路由实测 112 个问题一次要 1.36–1.45s，是装配期固定开销的大头。3.1 修好后实测裁剪到 20 / 40 候选的耗时与命中率，再决定默认值。

**验收**：给出裁剪前后的延迟与命中对照；默认值有依据（改或明确不改）。

**结论（2026-09-20，`pnpm run probe:router-cost`）**：
- **裁剪前有真实缺陷**：短名单是词法的，而 7 条用例中 4 条是纯中文 ⇒ **一个可匹配词都没有**，'前 N 名'退化成**目录顺序前 N 项**。实测上限 20 → **4/7**（丢 `split-into-stories`、`pricing-change`、`press-release`），上限 40 → **5/7**。
- **修复**：请求不含拉丁词时**不做裁剪**（返回全部可载入候选），并钉了单测；"不做裁剪"比"假装目录顺序是排序"更诚实。
- **修复后**：0 / 20 / 40 三档都是 **7/7**；但守卫让 **5/7 条请求与不裁剪时逐字节相同**（问题数都是 92），真正被裁剪的 3 条是 **20 问 0.41–0.99s vs 92 问 0.79–2.32s**（中位数 838ms）。
- **默认值明确不改（仍为 0）**：① 平均延迟的下降主要来自那 3 条，且中位数 838ms 距 4000ms 预算有 4–5 倍余量；② 守卫只覆盖"完全没有拉丁词"，中英混写仍会被裁剪，风险未消除；③ 要改默认值需要一批真正的跨语言标注语料（现 7 条）。
- 方法论记录：探针**必须关掉客户端 30s 载荷缓存**（`cacheTtlMs: 0`）——第一版把没发生的网络调用报成 2ms。

见 `docs/calibration.md` §29 与 `docs/calibration/probe-2026-09-20-router-cost.json`。

## 批次 4 — `completion-guard`（唯一需要标定的新模块）

### [x] 4.1 先量假完成发生率

"agent 宣称做完了但没验证"（该轮无写操作、无测试输出、无读回）——我们的两类护栏都管不到：`loop-guard` 管重复/停滞，确定性外壳与 `safety-guard` 管单次调用的危险度。**发生率目前没有任何数据。**先从历史会话与决策日志机械统计该形态的频次与分布。

**判据**：样本稀少 → **不做**，把该结论写进 `research.md` 的未采纳表。

**结论（2026-09-20，`pnpm run probe:completion`）**：**样本稀少，判据触发 ⇒ 不做**。
- 先修掉了一个前提错误：`~/.dsh/sessions/**` 的 121 个 zstd 文件（30MB）**不含消息**，解压后只有一条 session 头记录（合计 23KB）；真正的逐轮文本在 `~/.dsh/storages/session_projcache/sessions/*.json` 的 `rows.turnOutline` 里，但 **response 被截断**（约 200 字符）。
- 探针测的是**"自称完成之后用户表达不满足"**（不是"断言为假"的证明），严格/宽松两套模式 + 全部命中对留档供人工复核。
- 实测：33 会话 / 354 turn（229 带用户 prompt）/ 32 条完成断言；其中**只有 11 条后面还有用户 turn**（可观测），严格纠正 **1**、宽松 2（含 1 条人工复核为假阳性）。唯一严格命中确为真：某轮自称"计划内已全部完成"，用户回"不合入…当前不算交付结束"。
- 不做的三条理由：可观测单元 11 个（置信区间宽到无法设阈值）；94% 的 response 被截断、且自主 goal 轮恰好没有人类纠正信号（用这份语料标定等于用假数据标定）；代价不对称（误报让本该结束的 turn 不结束）而收益证据强度是 1/11。
- 重开条件：用 `dsh-session-log-export` 导出**消息级**语料后重跑本探针；可观测样本达数百条且严格纠正占比可观时再评估 4.2。见 `docs/calibration.md` §30。

### [x] 4.2 若做：挂在 `agent/turn-stopping` 上 —— **判定：不做**（4.1 样本稀少）

- 锚点已查证：`agent/turn-stopping` 是宿主真实的 serial 事件（`dsh-agent-loop`），payload 的 `agent` 由 `dsh-scope` 的 scoped-event 解析器注入；强制继续的手法是 `agent.steer(createUserMessage(...))`（宿主自带的 Stop hook 通道就是这么做的）。
- 判别两问：① 本轮宣称的完成是否有证据；② 是否需要人介入（不可判定、要拍板）。只在**桶概率 + confidence 双达标**时注入一条纠偏，其余保持沉默。
- 复用已有资产：`evaluate*` 纯函数抽法、`cooldownSteps` / `minConfidence`、bench 语料驱动发布代码、`drill` 与 `verify:mutants` 各加条目。
- **形状先确认再写逻辑**（宿主源码 → `verify:dsh` 集成断言 → 单测）。本仓库两次最严重的缺陷都出自形状假设。
- **默认关闭或极保守**：误报会让本该结束的 turn 不结束，代价不对称。
- ⚠️ **不要跳过 4.1**：本项的"价值最高"是印象，不是证据——唯一外部依据是一个只有几次提交的小仓库，属形态示范；而"过早宣告完成"的发生率、以及宿主是否已有等价能力，我们都还没量过。

**结论**：4.1 触发"样本稀少 ⇒ 不做"，因此**本项未实现**（上面五条与锚点查证结果保留，作为将来重开时的起点）。未采纳的结论已写入 `docs/research.md` 的未采纳表，重开条件见 4.1 与 `docs/calibration.md` §30。
